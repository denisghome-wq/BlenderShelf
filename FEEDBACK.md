поступления, структурируем по фичам. **Пока это только сбор и анализ — по

по приоритету.

Формат записи: `[статус] Заголовок` + источник/дата + суть + (если есть)
техническая заметка о вероятной причине/реализации.

Статусы: `Idea` (хотелка, не спланировано) · `Bug?` (нужен репро) ·
`Planned` · `Done` · `Rejected`.

**Дизайн-принцип проекта (владелец, 2026-09-24):** Pie Menu Editor как
референс для механики — слишком переусложнённый аддон с полной
кастомизацией. BlenderShelf должен оставаться дружелюбнее и проще в
интерфейсе и опыте взаимодействия. При переносе любого паттерна из PME

## Вопрос: зачем нумерация кнопок шелфа?

Не хоткей — прочитано по коду (`draw_shelf()`, `__init__.py:1717-1726`
рисует `str(i + 1)` как декоративный текст поверх кнопки; `_draw_pie_slots()`,
`__init__.py:807-821`, точно так же пишет `f"{idx + 1}. {item.label}"` в
пай-меню, используя тот же индекс, что и на шелфе). Число — это только
визуальное соответствие "кнопка №N на шелфе = пункт №N в пай-меню" (важно
именно для пай-меню: `menu_pie()` раскладывает пункты по фиксированному
компасу W/E/S/N/NW/NE/SW/SE, который не совпадает с порядком слева-направо
или списком, так что без числа сопоставить пункт пай-меню с кнопкой шелфа
на глаз было бы неочевидно). К хоткеям никак не привязано, можно спокойно
выключить (`Show Number` в настройках), если не нужно.

Источник: вопрос от тестового пользователя, 2026-09-25.

## Фича: контекстно-зависимые наборы кнопок (Object/Edit/Sculpt/Shader Editor)

**[Idea] Разный набор кнопок/пунктов пай-меню в зависимости от режима**
(Object Mode vs Edit Mode на одних и тех же хоткеях), с расширением до
Sculpt Mode и Shader Editor.

- Источник: тестовый пользователь, 2026-09-24.
- Отдельно отмечено: ноды можно добавить в шелф (кнопка с командой,
  создающей ноды), но "вызвать" их потом кнопкой или через пай-меню в самом
  Shader Editor нельзя.
- Техническая причина последнего подтверждена по коду: шелф и модальный
  оператор жёстко привязаны к `SpaceView3D` —
  `bpy.types.SpaceView3D.draw_handler_add(draw_shelf, ...)` (`__init__.py:1578`),
  хоткей пай-меню зарегистрирован только в keymap `'3D View'` (`__init__.py:219`),
  и весь хит-тестинг/редрав фильтрует `area.type == 'VIEW_3D'` (несколько
  мест). В Shader Editor у оверлея сейчас просто нет точки входа — это не
  баг, а архитектурное ограничение текущей версии.
- Режим (Object/Edit/Sculpt) внутри VIEW_3D технически читается через
  `context.mode` / `obj.mode` — сама привязка набора кнопок к режиму не
  такая большая переработка, как мультименю выше, но требует решить: разный
  набор кнопок per-mode — это отдельная коллекция `buttons` на каждый режим,
  или один список с полем "в каких режимах показывать"?
- **Реализуемость подтверждена**: сам Pie Menu Editor умеет ровно это — его
  `keymap_helper.py` регистрирует хоткей с параметром `space_type`, а не
  хардкодом под VIEW_3D, то есть per-editor пай-меню — рабочий, проверенный
  паттерн, не гипотеза. Два разных по цене случая:
  1. Реакция только на **режим** внутри 3D-вьюпорта (Object/Edit/Sculpt) —
     дёшево, `context.mode` уже читается в момент клика, нужна только
     фильтрация набора кнопок перед показом.
  2. Реакция на **какой редактор** под курсором (Shader/Node Editor и т.п.) —
     **это относится к плавающему шелфу-оверлею**, не к пай-меню (см.
     уточнение ниже, они архитектурно разные). Для шелфа это дороже: свой
     `draw_handler_add` на каждый нужный `bpy.types.Space*` (например
     `SpaceNodeEditor`) плюс своя запись в keymap с `space_type='NODE_EDITOR'`.
     Главный компромисс: сейчас на весь аддон один постоянно живущий
     modal-оператор, привязанный к VIEW_3D; при расширении на другие
     редакторы его придётся размножить по типу области или сделать
     context-aware — а значит весь класс багов вроде "зомби при переключении
     workspace" (см. память проекта) нужно будет пере-верифицировать в
     каждом новом контексте, а не только в 3D-вьюпорте.

**Уточнение по владельцу проекта (2026-09-24): один хоткей, контекстно-зависимый
пай-меню** (эдит-мод открывает одно меню, объект-мод другое, отдельно для
Node/Shader Editor) — **для самой пай-меню это дёшево** и не требует ничего
из дорогого п.2 выше: `BLENDERSHELF_MT_pie` — обычный `bpy.types.Menu`,
вызывается штатным `wm.call_menu_pie`, клик по пункту идёт через обычный
`pie.operator("blender_shelf.run_command", ...)` (`__init__.py:591-619`) —
никакого `draw_handler_add`/кастомного хит-тестинга тут нет и не нужно, это
только у плавающего шелфа-оверлея.

Изучили, как это решает сам PME (по явной просьбе владельца — для
фич пай-меню всегда сверяться с исследованием PME, см. память
`feedback_pme_research_for_pie_features`) — и их подход лучше, чем ветвление
внутри одного `draw()`:

- PME хранит **несколько независимых определений пай-меню**
  (`types.py:PMItem`), каждое со своим `km_name` (в каком keymap/редакторе
  живёт) и своим `poll_cmd` — питоновским условием применимости к текущему
  контексту, компилируемым в `poll(cls, context)` (`types.py:462-480,
  713-730`).
- Несколько таких определений регистрируются **на один и тот же хоткей**
  (`register_hotkey()`, `types.py:737`) — каждое своей записью
  `keymap_items.new(...)`. При нажатии клавиши общий оператор-диспетчер
  `wm.pme_user_pie_menu_call` проверяет `poll()` каждого кандидата
  (`operators.py:2142`); не прошло — клавиша "проваливается" к следующему.
  Побеждает первое меню, чей `poll` истинен для текущего режима/редактора.
- Масштабируется чище, чем один разрастающийся `if/elif` в `draw()`: новый
  контекст — новое определение меню с условием, а не новая ветка в общем
  методе.
- **Облегчённая адаптация для BlenderShelf** (без веса произвольного
  exec'уемого `poll_cmd`, PME под это тащит отдельную инфраструктуру —
  словарь `poll_methods`, окружение `pme.context`): конечный список
  контекстов известен заранее (Object/Edit/Sculpt/Node Editor), значит
  вместо произвольной строки — простое enum-поле `context` на каждом
  определении пай-меню, проверяемое обычным `if`, без exec.
- Статус: направление согласовано, реализация не начата. Завязано на
  разделение шелф/пай-меню выше — "несколько определений пай-меню" естественно
  ложится поверх уже запланированного `prefs.pie_buttons`.

**Уточнение по владельцу проекта (2026-09-24): "Add to ShelfPie" в ПКМ-меню
должна сама понимать контекст и класть кнопку в нужную группу пай-меню.**
Два дешёвых пункта из этого предложения (третий — запись целого выделения
нод как единой воспроизводимой команды — отдельная, гораздо более тяжёлая
фича, в трекер сознательно не заносится, обсуждается отдельно при
необходимости):
1. **Автоопределение группы.** В момент клика `context.mode`/`context.area.type`
   известны точно, так что новую кнопку можно сразу пометить подходящей
   группой без участия пользователя — прямое применение poll-диспетчеризации
   из пункта выше, ничего сверх уже запланированного.
2. **Ручной выбор группы при добавлении.** Маленький диалог
   (`wm.invoke_props_dialog`) с выпадающим списком групп пай-меню, по
   умолчанию — автоопределённая из п.1, с возможностью переопределить.
- Статус: направление согласовано, реализация не начата.

**Анализ (2026-09-24): сколько групп пай-меню реально нужно по контексту.**
Сверено с живым Blender 4.4.3 через `bpy_api_lookup` (MCP), не по памяти:
- `Context.mode` (актуальный режим внутри 3D-вьюпорта) — **27 сырых enum-
  значений**: `EDIT_MESH, EDIT_CURVE, EDIT_CURVES, EDIT_SURFACE, EDIT_TEXT,
  EDIT_ARMATURE, EDIT_METABALL, EDIT_LATTICE, EDIT_GREASE_PENCIL,
  EDIT_POINT_CLOUD, POSE, SCULPT, PAINT_WEIGHT, PAINT_VERTEX, PAINT_TEXTURE,
  PARTICLE, OBJECT` + 10 значений Grease Pencil (дубли legacy GPv2
  `*_GPENCIL` и нового GPv3 `*_GREASE_PENCIL` для paint/edit/sculpt/weight/
  vertex).
- Это **не единственная ось** — `context.mode` вообще не покрывает, в каком
  редакторе (`space_type`) находится курсор: Node Editor (Shader/Geometry
  Nodes/Compositor, различаются через `space_data.tree_type`), Image Editor
  и т.д. — второе, отдельное измерение поверх режима.
- **1:1 маппинг "группа = сырой enum" — избыточен** и прямо противоречит
  принципу "проще и дружелюбнее PME" (см. шапку документа): пользователь
  никогда явно не просил Grease Pencil/particle-режимы, а legacy-дубли GPv2
  vs GPv3 для обычного пользователя вообще не должны быть видимым выбором.
- **Рекомендация — стартовать с малого, curated-набора, расширять по
  реальному запросу, а не заранее:**
  1. `OBJECT` — объектный режим
  2. `EDIT_MESH` — самый частый edit-режим (остальные `EDIT_*` — curve,
     armature, lattice и т.п. — по умолчанию не заводить отдельной группой,
     пока не попросят; это ниша)
  3. `SCULPT`
  4. `NODE_EDITOR` (изначально — Shader Editor, единственный, что
     запрашивали; Geometry Nodes/Compositor можно добавить туда же позже по
     `tree_type`, не обязательно сразу дробить)
  - **Решение владельца (2026-09-24): старт без пятой группы `ANY`** — пока
    4 группы (`OBJECT`, `EDIT_MESH`, `SCULPT`, `NODE_EDITOR`), без
    фолбэка "везде". Итого **4 группы на первую итерацию**, а не 27+. Paint-режимы
    (Vertex/Weight/Texture), Pose Mode, Grease Pencil — сознательно не
    включены в стартовый набор, добавляются по факту запроса, а не
    превентивно.
  - Архитектурная заметка на будущее: `space_type` и `mode` — две разные оси
    (редактор vs режим внутри редактора), а не один плоский список. Одно
    enum-поле "контекст", смешивающее оба измерения, будет путать при первом
    же появлении режима, специфичного не только для VIEW_3D — закладывать
    структуру с самого начала как (редактор, опционально — список режимов
    внутри него), а не как один общий enum.

**[Idea] Копировать/вставлять пункты пай-меню между группами** (владелец
проекта, 2026-09-24) — если функция применима в нескольких контекстах
(например и в Object, и в Edit Mode), вместо автоопределения "одна группа
на функцию" дать операцию "Copy to group", которая кладёт независимую копию
пункта в другую группу.

- Контекст: автоопределение при "Add to ShelfPie" читает `context.mode`
  только в момент клика — оно принципиально не может понять, что оператор
  работает и в других режимах тоже (Blender не даёт дёшево прогнать
  `operator.poll(context)` под другим режимом без реального переключения в
  него). Мультиселект-флаг (`EnumProperty(options={'ENUM_FLAG'})`) как
  альтернатива обсуждался, но по решению владельца в трекер не идёт —
  вместо этого пользователь просто копирует пункт вручную, когда ему это
  реально нужно.
- Реализация: та же форма, что уже есть у кнопок сегодня —
  `pref_add`/`pref_remove`/`pref_move` (`__init__.py:391-422`). Новый
  оператор "Copy to group" — тот же паттерн, только вместо пустой заготовки
  копирует поля (`label`/`icon_path`/`command`) существующего пункта в
  коллекцию целевой группы.
- Важный нюанс: копия **независимая**, не ссылка — правка команды в одной
  группе не обновляет копию в другой. Для простого "скопировать при
  необходимости" это ожидаемо; "редактирую в одном месте — меняется везде"
  была бы уже другая, более сложная фича (общая ссылка/шаринг), не
  копирование.
- Статус: направление согласовано, реализация не начата.

## Bug: команда через кнопку/пай-меню молча не выполняется (скрипт с `if __name__ == "__main__"`)

**[Bug] Причина подтверждена эмпирически (2026-09-24), больше не гипотеза.**
Изначально репро описывалось как "Apply from Script не применяет изменения"
— по факту это не баг конкретно `Apply from Script` (тот копирует текст
1:1 корректно), а баг в исполнении самой команды через клик, который
проявляется именно на скриптах, написанных по стандартному шаблону.

- Источник: тестовый пользователь, 2026-09-24, скрипт `MP_set.py`
  (добавляет Bevel + Weighted Normal модификаторы). Репро: добавил кнопку →
  написал скрипт через `Edit as Script` → прогнал `Play` в окне скрипта —
  сработало → `Apply from Script` → клик по кнопке шелфа/пай-меню — тишина,
  никакой ошибки не видно.
- **Подтверждённая причина**: скрипт определяет `add_bevel_modifier(context)`
  и вызывает её только внутри `if __name__ == "__main__":` — стандартная,
  повсеместная конвенция для самостоятельного скрипта. Клик исполняет
  команду через `_exec_shelf_command()` (`__init__.py:121-122`):
  `exec(command, {"bpy": _shelf_bpy})` — без `__name__` в globals вообще.
  Проверено на живом Python (чистая семантика `exec()`, не Blender-специфика):
  без `__name__` в переданном словаре глобальных имён `exec()` не бросает
  `NameError` — `__name__` тихо резолвится в `'builtins'`, так что
  `if __name__ == "__main__":` оказывается `False`, функция определяется, но
  никогда не вызывается. Ни исключения, ни `self.report({'ERROR'}, ...)` —

## Система: как узнать заранее, сломает ли захват кнопки похожий баг
## (SKIP_SAVE), не тестируя каждый оператор вживую

**Причина, а не догадка (по устройству Blender, подтверждено уже на 5
операторах — node.add_node, node.add_group, brush.asset_activate,
object.modifier_add, mesh.mark_sharp/mark_seam/merge, все 2026-09-24/25):**
`copy_python_command_button()` внутри дёргает Blender-функцию
`WM_operator_pystring`, которая **сознательно пропускает свойства с флагом
`SKIP_SAVE`** — флаг существует, чтобы разовое значение кнопки не
запоминалось как "последнее использованное" для следующего вызова того же
оператора. Именно то свойство, которым различаются пункты одного меню
(`clear`, `type`, `name` и т.п.), чаще всего и помечено `SKIP_SAVE` — по
той же причине, по которой его туда и поставили. Побочный эффект: ровно то
значение, которое нужно для честной репро-команды, чаще всего и пропадает.

**Как узнать заранее, до жалобы пользователя:**
1. Несколько разных пунктов меню зовут **один и тот же** `op_id`, различие
   только в свойстве (не разные классы операторов) — пример: весь Merge-меню
   это `bpy.ops.mesh.merge(type=...)`, не отдельные операторы на пункт.
2. Проверить живьём (Python-консоль Blender или Blender MCP):
   `bpy.types.<CLASS>.bl_rna.properties['<prop>'].is_skip_save` —
   `True` значит операция в зоне риска, можно сразу добавлять override в
   `_OPERATOR_OVERRIDES`, не дожидаясь репорта.

**Как узнать по уже пришедшему фидбеку, без повторного анализа с нуля:**
характерный симптом — "какой вариант ни добавляю, работает как один и тот
же" (например Clear Sharp сохраняется, но исполняется как Mark Sharp) — это
и есть сигнатура именно этого класса бага, можно сразу писать override по
готовому шаблону (`label_fn`/`command_fn`, читают различающее свойство через
`getattr(op, "<prop>", <default>)`), не перепроверяя `copy_python_command_button()`
заново.

Полная версия этой заметки — комментарий прямо в коде, над
`_OPERATOR_OVERRIDES` в `__init__.py` (там же, где добавляется каждый новый
override), синхронизировать оба места при изменении.

- Решение владельца (2026-09-25): точечные фиксы продолжаются по одному
  оператору, но теперь по этой системе — не с нуля каждый раз. Полная
  замена механизма захвата на универсальный (через `op.is_property_set()`
  вместо доверия `copy_python_command_button()`) обсуждалась и отложена —
  выше риск регресса на всех кнопках сразу, не только на проблемных.

  зависимости от таймеров/контекстных оверрайдов на нашей стороне.

  которые в шелфе/пае работают чуть иначе, чем нативный хоткей, и это
  осознанный, а не случайный компромисс.
- Если это когда-нибудь снова всплывёт: не пытаться чинить на уровне
  таймеров/контекста ещё раз — команда Blender это ограничение не считает
  багом уже 15 лет, шанс, что появится новый обходной путь именно для этого
  макроса, крайне низкий.

## Bug: иконки шелфа слетают после Export/Import Settings на другой машине

**[Done, подтверждено логикой + юнит-тестом функций в изоляции] Исправлено
(2026-09-25). Не проверено вживую через реальный Export→Import между двумя
машинами — Blender MCP видит только одну текущую сессию.**

- Источник: тестовый пользователь, 2026-09-25. Репро: настроил шелф дома,
  Export Settings → перенёс JSON на рабочий ПК → Import Settings → все
  настройки (позиция, цвета, кнопки, команды) встали корректно, но у всех
  кнопок пропали иконки. Пользователь сам верно предположил причину: путь
  до каждой иконки жёстко прописан, не относителен.
- **Подтверждено чтением кода, гипотеза верна:** `icon_path` каждой кнопки
  — абсолютный путь, посчитанный через `os.path.dirname(__file__)` в
  момент создания кнопки (`ADDON_DIR`/`ICON_DIR`/`BLENDER_ICON_DIR`,
  `__init__.py:23-24,182`) — то есть буквально
  `C:\Users\<логин>\AppData\Roaming\Blender Foundation\...\icons\blender\
  MESH_CUBE.png`. `_serialize_items()`/`_deserialize_items()` (общие для
  локального `shelf_config.json` и для Export/Import Settings) писали и
  читали эту строку один в один, без какой-либо релятивизации. Домашний и
  рабочий Windows-логины (или просто расположение профиля) отличаются →
  путь из экспортированного JSON на другой машине не существует.
- **Фикс:** новые `_portable_icon_path()`/`_resolve_icon_path()`
  (`__init__.py`, прямо перед `_serialize_items`). При сохранении — если
  `icon_path` указывает внутрь папки аддона (`icons/`), сохраняется
  **относительно** неё (например `"blender/MESH_CUBE.png"`); при загрузке
  такой относительный путь собирается обратно от `ICON_DIR` **текущей**
  машины — работает независимо от логина/расположения профиля, пока
  установлен тот же аддон (а он теперь несёт полный набор 672 иконок, см.
  секцию про пак иконок выше — на обеих машинах одинаковый набор файлов).
  Кастомная иконка, выбранная вне `icons/` (через "Pick Icon" на
  произвольный файл), остаётся абсолютным путём как раньше — принципиально
  не может стать портируемой, сам файл-то не переезжает вместе с JSON;
  это осталось как есть, не регрессия, а честное ограничение.
- **Самолечение уже сломанных конфигов**: `_resolve_icon_path()` при
  чтении абсолютного пути, которого не существует на этой машине, ищет
  файл с тем же именем в `icons/blender/` текущей установки — то есть
  JSON, экспортированный ДО этого фикса и уже когда-то сломавший иконки на
  импорте, начнёт работать сам, без необходимости переэкспортировать с
  исходной машины.
- **Проверено:** три сценария (свой встроенный путь → относительный →
  обратно абсолютный корректно; чужой абсолютный путь с другого логина →
  самолечение через совпадение имени файла; кастомная иконка вне `icons/`
  → остаётся абсолютной) — юнит-тестом самой логики в изоляции (чистый
  Python, без Blender, поскольку это чистые функции работы с путями).
  Синтаксис аддона проверен (`python -m py_compile`, passes). Бэкап:
  `backups/__init___20260925_<ts>_portable_icon_paths.py` (обе копии).
  Архив `BlenderShelf-releases/dist/BlenderShelf.zip` пересобран.
- **Не проверено:** реальный Export на одной установке → Import на другой
  установке Blender (например второй профиль/другая папка `%APPDATA%` на
  этой же машине, раз второй физической машины под рукой нет) — нужен
  живой тест пользователем на обеих его машинах после обновления аддона.

## Исследование: масштаб проблемы SKIP_SAVE-свойств по всему Blender

**По прямому вопросу владельца ("сколько ещё подобных функций") — не баг-репорт,
разведка масштаба. Ничего не фиксилось, только собрано и проверено.**

- Метод: статически просканировал весь `bl_ui`/`bl_operators` исходный код
  Blender (AST-разбор, не regex — искал `layout.operator("id.id")`, за
  которым в том же draw-методе следует `.prop = значение`, с несколькими
  такими вызовами одного и того же operator id, различающимися значением) —
  **219 operator id** в стоке Blender попадают под паттерн "один id, ≥2
  пункта меню, различаются только свойством" (это сам факт паттерна, ещё не
  доказательство бага — багом это становится только если различающее
  свойство помечено `SKIP_SAVE`).
- Для операторов из меню Normals (то самое меню с последнего репорта) и
  смежных частых случаев проверил `is_skip_save` живьём через Blender MCP
  (`bpy.ops.<id>.get_rna_type().properties[...]`, тот же метод, что уже
  описан в разделе "Система: как узнать заранее" выше):

**Подтверждённо сломано (`SKIP_SAVE=True` — copy_python_command_button()
теряет различающее свойство, тот же баг-класс, что node.add_node/mark_sharp/
mark_seam/merge/mod_weighted_strength):**
- **`mesh.select_all` / `object.select_all`, свойство `action`
  (SELECT/DESELECT/INVERT/TOGGLE) — САМЫЙ ШИРОКИЙ по охвату случай.** Тот же
  ровно паттерн (`action`, `SKIP_SAVE=True`) переиспользуется буквально
  везде: `curve.select_all`, `pose.select_all`, `particle.select_all`,
  `armature.select_all`, `grease_pencil.select_all`, `paint.face_select_all`,
  `paint.vert_select_all`, `curves.select_all`, `mball.select_all`,
  `lattice.select_all`, `uv.select_all`, `clip.select_all`,
  `action.select_all`, `graph.select_all`, `nla.select_all`,
  `sequencer.select_all`, `file.select_all`, `info.select_all` и другие —
  везде тот же принцип "Select All / Deselect All / Invert" одним operator
  id. Если пользователь когда-нибудь попробует добавить "Select All"/
  "Invert Selection" на шелф из любого такого меню — типичный
  кандидат, гораздо вероятнее, чем Freestyle-специфичные пункты ниже.
  **Не пофикшено, не запрошено явно — только зафиксировано.**
- **`mesh.mark_sharp`, свойство `use_verts` — брешь в уже существующем
  фиксе.** Наш собственный `_mark_sharp_command()` (`__init__.py`, override
  из сессии 2026-09-25) читает только `clear`, но меню реально предлагает и
  **вершинный** вариант (`use_verts=True`, отдельные "Mark/Clear Sharp
  Vertices" пункты, 3 варианта всего: `{clear}`, `{use_verts, clear}`,
  `{use_verts}`) — `use_verts` подтверждён `SKIP_SAVE=True` живьём. То есть
  если пользователь когда-нибудь попробует добавить именно вершинный
  вариант — получит тот же класс бага, что мы только что чинили для
  Select/Set Face Strength, потому что override неполный. **Требует такого
  же точечного патча**, как остальные записи в `_OPERATOR_OVERRIDES`.
- `mesh.mark_freestyle_edge` / `mesh.mark_freestyle_face`, свойство
  `clear` — тот же паттерн, что `mark_sharp`/`mark_seam`, не
  оверрайднуто вообще. Актуально только если пользователь занимается
  Freestyle NPR-рендером — низкий приоритет, если не попросит.
- `mesh.delete`, свойство `type` (Vertices/Edges/Faces/Only Edges & Faces/
  Only Faces из меню Delete, клавиша X) — часто используемое меню, не
  оверрайднуто. Реальный кандидат, если пользователь захочет вынести
  конкретный вариант Delete на шелф отдельной кнопкой.
- `mesh.select_mode`, свойство `type` (Vertex/Edge/Face select) —
  технически то же самое, но на практике это иконки в хедере, а не
  текстовый пункт меню — маловероятно, что кто-то жмёт правой кнопкой
  именно по ним через "Add to Shelf". Низкий приоритет.

**Проверено и подтверждено БЕЗОПАСНЫМ (`SKIP_SAVE=False` — базовый захват
`copy_python_command_button()` и так работает корректно, оверрайд не
нужен):** `mesh.bevel` (`affect`), `mesh.edge_rotate` (`use_ccw`),
`mesh.average_normals` (`average_type`), `mesh.normals_make_consistent`
(`inside` — это "Recalculate Outside/Inside", то же меню Normals),
`mesh.normals_tools` (`mode` — "Copy/Paste/Reset Vectors", тоже то же
меню), `mesh.edge_split`/`object.convert`/`object.make_links_data`/
`object.parent_set`/`object.parent_clear`/`object.track_set` (`type`/
`target`), `object.shape_key_move`/`object.vertex_group_move`/
`object.material_slot_move` (`direction`/`type`), `mesh.select_similar`
(`type`). **Хорошая новость по последнему репорту конкретно:** все
остальные пункты того же меню Normals, что "Set/Select by Face Strength"
(Recalculate Outside/Inside, Copy/Paste/Reset Vectors, Average) —

## Bug: аддон не различает Bevel Vertices и Bevel Edges

**[Done, подтверждено живьём] Исправлено (2026-09-25).**

- Источник: тестовый пользователь, 2026-09-25. Симптом — та же сигнатура,
  что уже не раз встречалась: обе кнопки (Bevel Vertices / Bevel Edges)
  вели себя одинаково.
- **Важное расхождение с разведкой:** `mesh.bevel`/`affect` ранее в этой же
  сессии проверялся через `is_skip_save` и был отмечен как **безопасный**
  (`SKIP_SAVE=False`) — то есть по нашей собственной модели бага
  (SKIP_SAVE-флаг роняет свойство при захвате) он не должен был ломаться.
  Реальный отчёт пользователя ему противоречит — значит, модель "только
  SKIP_SAVE" неполная, у `copy_python_command_button()` есть и другие пути
  терять/путать свойства, которые мы не до конца понимаем. **Не стали
  докапываться до точного альтернативного механизма** — по уже принятому
  в проекте правилу (характерный симптом = сразу override по шаблону, не
  передиагностируя `copy_python_command_button()` с нуля) сразу добавили
  `_bevel_label()`/`_bevel_command()` в `_OPERATOR_OVERRIDES`, читающие
  `affect` прямо с кнопки.
- **Единственный случай в этой сессии, где после фикса всё равно
  прогнали живую поведенческую проверку**, а не только синтаксис — потому
  что теория "почему сломано" не сошлась с репортом, и стоило убедиться,
  что сам фикс (а не только предположение о причине) реально работает:
  на кубе с полностью выделенной геометрией `affect='VERTICES'` дал 24
  вершины/14 граней, `affect='EDGES'` — 24 вершины/26 граней на той же
  исходной геометрии — подтверждённо разное поведение. Тестовые правки
  геометрии куба отменены, сцена пользователя не пострадала.
  - Первая попытка теста дала ложный результат (VERTICES сработал, EDGES
    — нет, оба варианта выглядели "как будто не то") из-за собственной
    ошибки методологии: выделялись только вершины bmesh
    (`v.select = True`) без `bm.select_flush()`, из-за чего рёбра/грани
    оставались невыделенными и `affect='EDGES'` бевелил пустое
    множество. Не баг аддона — баг тестового скрипта, найден и исправлен
    в этой же сессии до итоговых выводов.
- `mesh.bevel` уже получает автоматический `'INVOKE_DEFAULT'` через
  `_op_is_modal()` (несёт `BLOCKING`/`GRAB_CURSOR` в `bl_options`) —
  override не задаёт контекст сам, полагается на этот же обёрточный
  механизм, как и остальные interactive-операторы.
  Синтаксис проверен. Бэкап:
  `backups/__init___20260925_<ts>_bevel_affect_override.py` (обе копии).
  Архив `BlenderShelf-releases/dist/BlenderShelf.zip` пересобран.
